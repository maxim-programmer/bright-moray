# Логирование

Бэкенд пишет структурированные логи через [`uber-go/zap`](https://github.com/uber-go/zap).
Код — пакет `backend/logging`.

## Куда пишется

Одна запись уходит сразу в два приёмника (`zapcore.NewTee`) с **одинаковым набором полей**:

| Приёмник | Формат | Для чего |
|---|---|---|
| stdout | Console: `ts  LEVEL  caller  msg  {поля}` | человек, `docker compose logs` |
| файл `LOG_FILE` | JSON, одна запись на строку | машины, позже Loki |

Различается только представление: в консоли уровень заглавными (с цветом в терминале),
в JSON — строчными, время в JSON в UTC. Ключи общие, потому что у обеих веток одна база
`EncoderConfig`, а `service` и `component` добавляются на уровне логгера.

Настройка (переменные окружения):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn` или `error`; другое значение — ошибка старта |
| `LOG_FILE` | пусто | путь к JSON-файлу; пусто — только stdout. В Docker: `/data/logs/app.log` |

Если файл задан, но недоступен, сервер не запускается: молча потерять логи хуже, чем
заметить ошибку при старте.

## Поля

| Группа | Поля | Когда |
|---|---|---|
| Всегда | `ts`, `level`, `caller`, `msg`, `service`, `component` | на каждой записи |
| Запрос | `request_id`, `user_id` | любая запись, написанная внутри запроса; `user_id` — когда пользователь известен |
| Access-запись | `method`, `path`, `status_code`, `duration_ms`, `client_ip` | одна запись на запрос |
| По необходимости | `error`, `lot_id`, `stacktrace` | `stacktrace` — только у panic |

Правила:

- `msg` — короткая константа, **все значения в полях**. Интерполяция в сообщение ломает
  группировку и поиск.
- `duration_ms` — число с дробной частью (`0.217`): быстрые запросы иначе дали бы 0.
- `path` без query-строки. Не логируются пароли, токены, cookie, тела запросов, имена и
  контакты пользователей — только `user_id`.
- `component`: `main`, `middleware`, `handler`, `auth`, `live`, `server`.

Пример (одна и та же запись в двух форматах):

```
2026-11-19T11:47:18.097Z	INFO	handler/middleware.go:110	http request	{"service": "auction", "request_id": "9f2c1a7be3d44a50a1c2d3e4f5a6b7c8", "user_id": 42, "component": "middleware", "method": "POST", "path": "/api/lots/17/bids", "status_code": 201, "duration_ms": 0.217, "client_ip": "203.0.113.5"}
```

```json
{"level":"info","ts":"2026-11-19T11:47:18.097Z","caller":"handler/middleware.go:110","msg":"http request","service":"auction","request_id":"9f2c1a7be3d44a50a1c2d3e4f5a6b7c8","user_id":42,"component":"middleware","method":"POST","path":"/api/lots/17/bids","status_code":201,"duration_ms":0.217,"client_ip":"203.0.113.5"}
```

## request_id

1. `Middleware` берёт `X-Request-Id` от nginx (`$request_id`), если он безопасен
   (`[A-Za-z0-9_-]`, 8–64 символа), иначе генерирует свой (16 байт, hex).
2. Идентификатор кладётся в `context.Context` и возвращается клиенту в заголовке
   `X-Request-Id` — по нему обращение пользователя находится в логах.
3. Везде, где есть `ctx`, логгер берётся так:
   `logging.FromContext(ctx, logging.ComponentHandler)`. Слой `db` уже принимает `ctx`,
   поэтому сигнатуры не менялись; сам `db` ничего не логирует, а возвращает ошибки.
4. `user_id` становится известен после проверки токена: `Handler.userID` вызывает
   `logging.SetUser`, и последующие записи запроса получают `user_id`.
5. WebSocket-соединение наследует `request_id` рукопожатия: ставки по WS связываются
   с записью `GET /api/ws`. Таймеры и фоновые задачи запроса не имеют, у них только
   `component` и `lot_id`.

## Уровни

| Уровень | Что |
|---|---|
| DEBUG | выключен по умолчанию: `/health`, подключение и отключение WebSocket |
| INFO | старт и остановка, access-записи (`<500`), бизнес-события (лот создан, ставка принята, лот отменён, аукцион завершён), загрузка файла, очистка сессий |
| WARN | обработано, но ненормально или важно для безопасности: повторное использование refresh-токена, не удалось закрыть прежнюю сессию, отключён медленный WS-клиент |
| ERROR | операция сорвалась: 5xx, panic, ошибки БД |
| FATAL | только в `main` до запуска сервера |

4xx — это INFO: для приложения 401 нормален (access-токен живёт 15 минут, затем клиент
обновляет сессию). Опасные события пишутся на WARN в месте обнаружения.

## Ошибки и panic

- Ошибка, определившая ответ (5xx), не логируется отдельно: `fail(w, r, err)` запоминает её
  в состоянии запроса, а `Middleware` пишет **одну** запись с методом, путём, статусом,
  временем и `error`. Одна неудача — одна ERROR-запись.
- Ошибка, которая не повлияла на ответ (деградация), логируется сразу на WARN.
- Panic: `Middleware` пишет ERROR со `stacktrace`, отвечает 500 без подробностей и пишет
  обычную access-запись. `http.ErrAbortHandler` пробрасывается дальше как штатный обрыв.
- Panic в горутинах вне запроса (таймеры хаба) этим не ловится и роняет процесс; аварийный
  вывод рантайма идёт в stderr, а не в JSON-файл — его смотреть в `docker compose logs`.

## Ротация

Файл ротируется внутри процесса (`gopkg.in/natefinch/lumberjack.v2`): 100 МБ на файл,
5 архивов, не старше 14 дней, архивы сжимаются. Параметры — константы в
`backend/logging/logging.go`.

## Просмотр

```sh
docker compose logs -f backend                                 # консольный формат
docker compose exec backend tail -f /data/logs/app.log         # JSON
docker compose exec backend grep '"request_id":"<id>"' /data/logs/app.log
```

## Подготовка к Grafana + Loki

Loki пока не подключён, но формат готов: одна JSON-запись на строку со стабильными ключами.
Когда понадобится, в метки (labels) стоит брать только `service` и `level`;
`request_id`, `user_id` и `path` — в теле записи, у них высокая кардинальность.
Сборщик (Promtail/Alloy) читает том `logs_data`, ротацию файла он переживает.
