# Авторизация: access- и refresh-токены

## Схема
| | Access-токен | Refresh-токен |
|---|---|---|
| Формат | JWT, HS256 (`typ: at+jwt`) | 32 случайных байта, base64url (43 символа) |
| Claims | `sub` (id), `exp`, `iat`, `jti`, `iss`, `aud` | — (непрозрачный) |
| Срок | 15 минут | 7 суток бездействия, но не дольше 30 суток с момента входа |
| Cookie | `session`, `Path=/` | `refresh_token`, `Path=/api/auth` |
| Флаги | `HttpOnly; SameSite=Lax; Secure` (при `COOKIE_SECURE=true`) | те же |
| Хранение на сервере | нет (проверка подписи, БД не нужна) | только SHA-256 хеш, таблица `refresh_tokens` |
| Для чего | доступ к API и WebSocket | только `POST /api/auth/refresh`, `logout`, `logout-all` |

Refresh-cookie не уходит ни на `/api/lots`, ни на `/api/ws` — её видят только маршруты `/api/auth/*`.
Access-токен проверяется строго: алгоритм и тип зашиты в код (`alg=none`, `RS256`, `HS512` и т.п. отвергаются),
сверяются подпись (за постоянное время), `iss`, `aud`, `sub`, `jti`, `iat`, `exp`. Refresh-токен как access не пройдёт:
это не JWT.

## Сессии и ротация
Вход/регистрация создают *семейство* токенов (`family_id`). Каждый `POST /auth/refresh` в одной транзакции под
блокировкой строки (`SELECT … FOR UPDATE`) помечает предъявленный токен использованным (`used_at`, `replaced_by`) и
выпускает следующий в том же семействе. Если предъявляется **уже использованный** токен — это признак кражи:
всё семейство отзывается (`revoked_reason = reuse_detected`), cookie стираются, ответ `401 refresh_reused`.
История использованных токенов хранится до `family_expires_at` + 7 суток, затем её удаляет фоновая очистка (раз в час).

*Окно гонки* (`REFRESH_REUSE_GAP_SEC`, по умолчанию 10 с): если токен использован только что, повтор не считается
кражей — ответ `409 refresh_conflict`, ничего не отзывается и токены не выдаются. Это случай двух вкладок, обновляющихся
одновременно: cookie общие, вторая вкладка просто повторяет запрос. `0` — строгий режим без окна.

| Событие | Результат |
|---|---|
| `logout` | отзыв семейства текущей сессии (по refresh-cookie; access не нужен) |
| `logout-all` | отзыв всех сессий пользователя (по access-токену, а если он истёк — по действующему refresh) |
| смена пароля | отзыв всех сессий в той же транзакции, что и смена; **этому устройству сразу выдаётся новая сессия** |
| повторный вход в том же браузере | прежняя сессия этого браузера закрывается (`relogin`) |

Ограничение, присущее access-JWT без состояния: уже выданный access-токен действует до своего `exp` (≤ 15 минут)
даже после выхода или отзыва. Открытый WebSocket аутентифицируется один раз при подключении.

## CSRF, Origin, CORS
Все запросы кроме GET/HEAD/OPTIONS проходят проверку источника (`handler.Guard`):
`Sec-Fetch-Site: same-origin`, либо `Origin` с тем же хостом (без порта — как у WebSocket), либо Origin из
`ALLOWED_ORIGINS`; иначе `403 bad_origin`. Запросы без `Origin` и `Sec-Fetch-Site` (curl, мобильные клиенты) пропускаются.
Для Origin из `ALLOWED_ORIGINS` включается CORS с `Access-Control-Allow-Credentials: true` и точным значением
Origin (никогда `*`), обрабатывается preflight. Cookie с `SameSite=Lax` кросс-*сайтовые* запросы всё равно не получат,
поэтому `ALLOWED_ORIGINS` нужен для кросс-*доменных*, но same-site схем (поддомены, `localhost` на разных портах).

## Для фронтенда
1. Все запросы — с `credentials: 'include'` (при одном origin через nginx — по умолчанию). Токены в JS не доступны и
   в localStorage/sessionStorage не кладутся.
2. При старте — `GET /api/auth/me`; 401 → один `POST /api/auth/refresh`; успех → повторить `me`; `401` → показать вход.
3. Любой API-запрос, получивший 401: один `POST /api/auth/refresh` (общий для всех одновременных запросов —
   single-flight, например одним промисом), затем повтор исходного запроса один раз. 401 от самого refresh — выход
   из аккаунта (cookie уже стёрты сервером).
4. `409 refresh_conflict`: подождать 100–300 мс и повторить исходный запрос (cookie уже обновлены другой вкладкой);
   если снова 401 — вызвать refresh ещё раз.
5. Запланировать обновление можно по `accessExpiresAt` (мс Unix) из ответа refresh, но надёжнее реагировать на 401.
6. После смены пароля (`PUT /me/password`) устройство остаётся авторизованным, ничего перелогинивать не нужно.
7. WebSocket: после refresh переподключаться не обязательно, но новое подключение берёт свежую cookie.
